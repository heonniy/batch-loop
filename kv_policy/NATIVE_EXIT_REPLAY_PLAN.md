# Native exits + recorded replay for Full / Last / Loop1-all (2026-10-28)

## Verified upstream rules

- **Ouro:** learned ACT ponder/exit gate. At loop r the gate produces cumulative
  mass C_r; q-exit returns the first loop where C_r >= q, subject to
  minimum depth and maximum R=4. q=1 is fixed-depth baseline.
  Official HF model may **compute all R loops even when selecting a shallower
  output**: do not infer FLOP savings from gate output alone.
  References: https://ouro-llm.github.io/ and pinned ByteDance/Ouro remote code.
- **Huginn:** no learned Ouro-style ACT exit head. The official
  `raven_modeling_minimal.py` provides `get_adaptive_exit_evaluator` with
  `cosine` (auto 1e-3, distance = 1 - mean token cosine between
  successive latents), `kl`, `minp-kl`, `latent-diff`,
  `entropy-diff`, and `argmax-stability` (auto five unchanged steps).
  Primary: official **cosine auto**; sensitivity: KL and argmax stability.
  See: https://huggingface.co/tomg-group-umd/huginn-0125/blob/main/raven_modeling_minimal.py

## Phase A: trace generation (NOT yet wired into the existing Runner)

Use pinned official remote model code on a frozen FULL/strict teacher forcing
trajectory, separate prompt and decode decisions. Record each token ID,
all exit signals by recurrence, selected depth, q/threshold, model checkpoint
revision, prompt hash, and token position. Native Ouro gate must be read from
the model's learned ponder head, not approximated by logit confidence.
For Huginn, use the exact official evaluator initialisation and recurrence
index conventions. Defaults to 4 loops for Ouro and R32 for Huginn.

**Important:** an exit trace recorded with FULL cannot be assumed to be
the exit decisions that LAST or Loop1-all would make online. This is an
offline *counterfactual replay*, not live adaptive inference.

## Phase B: replay (requires a new variable-depth KV runtime)

Same frozen token sequence and per-position exit depth in every policy:
1. FULL dynamic: query recurrence r reads historical KV at min(r,d_i)
   for previously completed token i (explicit best-available rule).
2. LAST dynamic: query recurrence r reads historical KV at d_i.
3. Loop1-all dynamic: for r=1 read historical recurrence-1 KV; otherwise
   read historical KV at d_i. For tokens which executed only r=1 these coincide.

Require **token-major prompt prefill** for all three conditions; disallow
future read, and do not compute any loops > d_i solely to fill cache.
When a token exits the recurrence, its selected step's logits go to coda.
Current-token self K/V are always generated by its own executed step.
Ouro's output gate and Huginn's convergence gate have different semantics.

For fair results distinguish:
- teacher-forced replay: identical input tokens and exit trace across policies;
- free generation replay: depths indexed by decode position, but tokens are
  permitted to diverge. Trace beyond its original length MUST error rather
  than silently clamp, unless a fixed explicit extension policy is registered.
- live exits: recompute signals per policy; separate experiment.

Use identical B1/FP32 FULL parity to official code and small toy dictionary
cache test before full BF16 quality run. With a fixed depth of R for every
token the new policies must exactly reduce to existing FULL/strict,
LAST/strict, bankR1all/strict. This is a mandatory implementation gate.

## Proposed experiment

Ouro 1.4B/2.6B trained gate: q in {.5, .7, .9, 1.0}.
Huginn: official cosine auto and 2 nearby thresholds, plus argmax stability
as a sensitivity check. Evaluate 32-item pilot, then GSM8K-200/MATH500-200.
Report mean depth, histogram by token/prompt, NLL and Accuracy, generation
length, same-prefix KL, retained KV, actual execution counts.
For conditional FIRST-bank protection use the `bankR1all` registry
currently deployed for fixed R.

The *existing* `kv_policy/kvp/engine.py` executes every recurrence;
`kv_policy/kvp/native_exit.py` currently supplies validated gate selection
and trace identity formats only. **DO NOT report dynamic-depth accuracy or
claim physically skipped recurrences until Phase A/B are implemented and
run.** The tests cover utility semantics, not an end-to-end dynamic runtime.
